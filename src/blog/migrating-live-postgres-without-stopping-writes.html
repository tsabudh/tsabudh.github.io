A measured PostgreSQL migration: pg_dump and pg_restore against logical replication at 399 MB and 79 GB, with the cutover procedure and the failure modes found along the way.

The obvious way to move a database is to dump it, restore it, and point the application at the new one. I did that first and measured it. On a 399 MB database, writes were refused for at least 175 seconds. On 79 GB, they were refused for 62 minutes.

The problem is not that pg_dump is slow. It is that the copy happens inside the window where writes are refused. Logical replication moves the copy outside that window. The target is kept current while the source stays live, so at cutover the data is already there.

Same databases, same hardware, second method: 12.4 seconds at 399 MB, 23.2 seconds at 79 GB. Most of that was the application process restarting and me typing.

399 MB79 GBgrowth
dump + restore, write downtime≥175 s3,740 s21×
logical replication, write downtime12.4 s23.2 s1.9×

Data grew 200×. The dump-and-restore window grew with it. The replication window barely moved, and what growth it had came from things that are not a function of data size.

Here is the procedure, with the things that broke.

The setup

Two Postgres 18 clusters on one machine: the source on port 5442 with wal_level = logical, the target on 5443. An Express app with node-postgres in front, pool of 10.

A load generator ran a read loop and a write loop against the app, each about ten requests a second with a 2-second timeout, logging every attempt. Downtime is the gap between the last successful request and the next one, measured from the client side. Timeouts count as failures.

Before trusting that number I calibrated it: stop the database for a known 20 seconds, no migration involved. It read 20,372 ms. The extra 372 ms is the first successful poll landing after the restart.

The large dataset was a ballast table of 260 million rows of repeat(md5(random()::text), 8), 79 GB on disk, loaded in 26 batches of 10 million, each its own transaction.

Method 1: dump and restore

Freeze writes, pg_dump -Fc --no-acl, recreate the target, pg_restore, repoint the app, restart it, unfreeze.

pg_dump      9m47.504s   (user 9m29.533s, sys 0m17.689s)
pg_restore  20m16.564s   (user 1m59.208s, sys 0m12.186s)
dump file    6.0 GB

The two halves are bound by different things.

  • The dump was CPU-bound. User time was 97% of wall clock. That is compression, not disk. -Z0 would trade file size for time.
  • The restore was server-bound. User time was 10% of wall clock: pg_restore sat idle while the server loaded rows and rebuilt indexes. -j N parallelises this half. I did not use it, so this is the plain-restore number.

That is 30 minutes of copying. The other 30 of the 62 were human: two cancelled restore attempts, password prompts, checking file sizes between steps. Which is honest, because that is what a manual cutover looks like at 2 a.m. Every minute of it is a minute of refused writes.

WRITE   attempts 37348   succeeded 598   failed 36750
        longest gap 3,740,060 ms
        failure modes: 36721 × permission denied, 29 × fetch failed

Reads stayed up for all but 3 seconds, which is the point: dump and restore is not an outage for readers, it is an outage for writers, and it scales with the size of the data.

Method 2: logical replication

What you need first

The source needs wal_level = logical in postgresql.conf. This requires a restart, so do it before you need it.

SHOW wal_level;   -- must say 'logical', not 'replica'

If it still says replica after you edited the config, run SHOW config_file. You edited a different file than the one the server is reading.

The target needs the schema already in place. Logical replication copies rows, not table definitions. Run your DDL there first.

Both need a role that can connect over TCP. Test the connection string on its own before putting it anywhere else:

psql "host=SOURCE port=5442 dbname=mydb user=migrator password=..." -c "select 1"

That string is what the subscription will use. Debugging it standalone takes a minute. Debugging it wrapped in CREATE SUBSCRIPTION takes an hour.

Step 1: Publish on the source

CREATE PUBLICATION mypub FOR ALL TABLES;

FOR ALL TABLES requires superuser. A named-table publication does not, if you own the tables.

Check every table has a primary key before you do this. A table without one will replicate inserts and then refuse updates:

ERROR:  cannot update table "no_pk" because it does not have a replica
        identity and publishes updates

Logical replication does not ship SQL. It ships row messages, and an UPDATE carries an "old tuple" so the target knows which row to change. Replica identity is the rule for what goes in it, and it defaults to the primary key. No primary key, nothing to send, operation refused.

The refusal happens on the source, at statement time, before any WAL is written. Postgres will not emit WAL it knows cannot be applied.

Two ways out:

ALTER TABLE t REPLICA IDENTITY FULL;              -- whole row as identifier
ALTER TABLE t REPLICA IDENTITY USING INDEX idx;   -- a unique NOT NULL index

FULL always works and is expensive: every column written twice on every update, and the target matches by scanning. Prefer the index.

The trap is that inserts need no identity, so the table looks healthy until someone runs their first update. Find these before the publication, not after.

Step 2: Subscribe on the target

CREATE SUBSCRIPTION mysub
  CONNECTION 'host=SOURCE port=5442 dbname=mydb user=migrator password=...'
  PUBLICATION mypub;

This needs pg_create_subscription plus CREATE on the database:

GRANT pg_create_subscription TO migrator;

The statement runs on the target but creates a replication slot on the source. Remember that. It is the source's disk that pays for it.

The initial copy starts immediately and runs in the background. Watch it:

-- on the target
SELECT * FROM pg_stat_subscription;
SELECT count(*) FROM mytable;

A non-null pid means a worker is alive. Null means it died, and the target's log says why.

At 79 GB, with the source serving writes the whole time:

09:03:26  subscription created, slot created on publisher
09:05     target ballast   9.9 GB
09:10:13  target ballast  45 GB
09:17:24  target ballast  80 GB, tablesync slot gone

About 14 minutes, against 30 for dump and restore on identical data, and zero downtime during it. It is faster because nothing is compressed to a file and read back. Rows go straight from one server's heap to the other's.

During the copy you will see a second slot on the source named pg_<subid>_sync_<relid>_<n>, showing active = f between worker cycles. It looks like an orphan. It is not. It is the per-table sync slot, and it disappears when its table finishes.

I expected the main slot to hold back WAL for the whole 14 minutes. It did not. It stayed flat between 25 and 48 kB. The tablesync slot carried the cost, and it peaked at about 2 MB. Retained WAL scales with write rate, not data volume. At ten writes a second it is negligible. At production write rates, it is the number to watch.

If you add a table after this point, the target will not pick it up on its own. FOR ALL TABLES is dynamic on the publisher and static on the subscriber:

ALTER SUBSCRIPTION mysub REFRESH PUBLICATION;

Step 3: Confirm it is streaming

The initial copy finishing is not the same as replication working. Test a change made after the copy:

-- source
INSERT INTO mytable (col) VALUES ('probe');
-- target, within a second
SELECT * FROM mytable WHERE col = 'probe';

Then look at the slot on the source:

SELECT slot_name, plugin, active, restart_lsn, confirmed_flush_lsn
FROM pg_replication_slots;
 slot_name |  plugin  | active | restart_lsn | confirmed_flush_lsn
-----------+----------+--------+-------------+---------------------
 mysub     | pgoutput | t      | 0/43D71C38  | 0/43D71C70

Two numbers to understand, because you will use both:

  • confirmed_flush_lsn is how far the target has acknowledged. This is what you wait on at cutover.
  • restart_lsn is the oldest WAL the source must keep. This is what fills your disk.

While you wait: two things that will bite

Replication may run for hours or days before you cut over. Two failure modes live in that window.

Do not run DDL on the source

Add a column on the source and the target's apply worker dies:

ERROR:  logical replication target relation "public.events" is missing
        replicated column: "note"
CONTEXT:  ... in transaction 670078, finished at 0/43E54D90
background worker "logical replication apply worker" exited with exit code 1

It restarts every five seconds, hits the same transaction, dies again. Indefinitely. It never advances confirmed_flush_lsn, so WAL piles up on the source at whatever rate you write. I measured about 150 kB/min on a nearly idle system.

active flaps between true and false as the worker cycles, so it is useless as an alarm. Only retained WAL tells the truth.

Reverting the DDL on the source does not fix this. I tried. WAL is immutable, including its record of the table's shape, so replaying that transaction replays the schema as it was when written. The source no longer had the column and the target was still stuck on it.

The fix has to be on the subscriber:

-- on the TARGET
ALTER TABLE events ADD COLUMN note text;

One cycle later the worker gets past it and drains.

Which gives the ordering rule: add columns on the subscriber first, drop them there last. Once publisher-side DDL is in the WAL with rows behind it, the publisher can no longer help you.

Watch the slot

SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn))
       AS retained
FROM pg_replication_slots;

A slot overrides normal WAL recycling unconditionally. With the subscriber disabled, retained WAL went from 56 bytes to 187 kB with no application load at all, just autovacuum, checkpoints and catalog writes. Checkpoints run, data is safely on disk, and the source keeps the WAL anyway because a consumer promised to come back. There is no expiry and nothing cleans it up.

That is the correct behaviour. The alternative is a subscriber that reconnects and finds the WAL it needed deleted, with no way to know what it missed.

But it means a stalled or forgotten subscriber fills the source's disk, and when pg_wal is full Postgres cannot commit anything. You also cannot delete the files, because the slot still requires them.

Set max_slot_wal_keep_size if you would rather lose the subscriber than the primary. Alert on retained, not on active.

Step 4: Cut over

Lag should be near zero before you start. Run the whole sequence without pausing.

Freeze writes on the source. Revoking INSERT is one option and applies immediately to open connections:

REVOKE INSERT ON mytable FROM appuser;

Wait for the tail to drain. This is a comparison, not a sleep:

SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn))
FROM pg_replication_slots;
-- 0 bytes

It will not always reach exactly zero on a busy system, since autovacuum and checkpoints keep writing. Wait for small and stable, not equal.

Fix the sequences. This step is not optional and it is the one people miss.

Sequences do not replicate. The target has every row. Its sequences are untouched:

source: last_value = 3480
target: last_value = 1
target: max(id)    = 3515

The first insert after cutover collides on the primary key, and so do the next 3,515. Every check you would think to run passes first: row counts match, data is identical, lag is zero.

Note the source's last_value is below the real max, because sequences allocate in cached blocks. Copying the source's value across still collides. Read the target's own data:

-- on the TARGET
SELECT setval('mytable_id_seq', (SELECT max(id) FROM mytable));

Default is_called is true, so the next value is max(id) + 1. Too high wastes ids and costs nothing. Too low breaks inserts.

Repoint the application. Then verify against the server rather than your config:

SELECT inet_server_port();

Grants do not replicate either, so the freeze you applied to the source never reached the target. Writes resume without intervention. (pg_dump does carry grants, which is why the dump method needed --no-acl.)

The 79 GB cutover:

lag at freeze    0 bytes
setval           12792

WRITE   attempts 12806   succeeded 12576   failed 230
        longest gap 23,200 ms
        failure modes: 175 × permission denied, 55 × fetch failed

Verified on the target afterwards: zero duplicates, zero stale reads, zero sequence drift, and every write the load generator logged as succeeded was present.

What the 23 seconds actually was

Not the copy. The copy left the window entirely. What remained was the application process restarting, plus the time it took me to run four commands by hand. That is why the window went from 12.4 to 23.2 seconds while the data grew 200×: I was slower at the keyboard, not the database slower at the cutover.

399 MB79 GBgrowth
dump time7.8 s587 s75×
restore time11.9 s1,216 s102×
replication initial copy (live)seconds840 s-
dump + restore, write downtime≥175 s3,740 s21×
replication, write downtime12.4 s23.2 s1.9×

Neither restart time nor typing speed is a database problem, which means the next improvement is not a database change. Put pgbouncer between the application and Postgres and the cutover becomes PAUSE, repoint, RESUME. One switch point, the application never restarts, and connected clients queue instead of failing. The pause stops being an error and becomes latency.

The first row of that table is copy time, and copy time scales with data. The second row does not, which is the entire point.

Two runs that measured nothing

Before the method was right, two runs produced numbers that looked fine and meant nothing.

  • No start bracket. Writes were frozen before the load generator started. Zero of 8,135 writes succeeded, so there was no success to measure a gap from. It reported 0 ms.
  • No stop bracket. 1,171 writes succeeded, then 713 were denied, but I stopped the generator before the flip completed. It reported 103 ms, which was the largest gap during the healthy period.

"Gap between consecutive successes" silently returns nonsense when either end is missing. Every valid run needs three phases: working, broken, working. The same is true of the ≥175 s in the small dump run: the log ended before the flip completed, so that number is a floor, not a measurement.

Caveats

  • Single machine, both clusters on the same NVMe device, competing for IO.
  • Write load around ten a second. WAL retention would look different under production traffic.
  • pg_restore ran without -j. Parallel restore would shrink the 20-minute figure, not the shape of the comparison.
  • Both cutovers include manual steps at a keyboard. Scripted, both would be shorter.
  • The ballast is md5 hex, which compresses about 13:1. Real data will not, so a real dump file will be larger and the dump will spend less time compressing and more time writing.

Postgres 18.6, two local clusters, Express with node-postgres. Downtime measured client-side from a JSONL log of every request, calibrated against a known 20-second stop.
